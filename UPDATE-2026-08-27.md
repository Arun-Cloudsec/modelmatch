## 1. Freshness and provenance

### Two dates, not one

`DATA_LAST_UPDATED` still said **May 9, 2026** while the catalogue had actually
been refreshed on 21 August. Anyone reading the site was told the data was six
weeks older than it was.

That single field conflated two different facts, so it is now split:

| Stamp | Value | What it means |
|---|---|---|
| `DATA_SYNC.priceVerified` | `2026-08-21` | Last time every per-token price was checked line-by-line against a live vendor pricing page |
| `DATA_SYNC.catalogSynced` | `2026-08-27` | Last time the model *list* was reviewed for additions, retirements and deprecations |

A sync can happen without a re-pricing pass. Showing one date for both would
have meant either overstating the price freshness or understating the catalogue
freshness — there was no honest single number.

### Provenance strip

A new bar sits directly under the top bar on every page (`#provBar`,
`renderProvenanceBar()`):

- **SOURCE** — vendor pricing and model documentation (hand-curated), AWS
  Bedrock / Azure AI Foundry / GCP Vertex region data, Core42 Compass, and the
  live OpenRouter + HuggingFace feeds.
- Both sync stamps, with a freshness dot: green ≤14 days, amber ≤45, red beyond.
- A link into the existing Sources & Methodology modal.

The modal now also explains what each of the three stamps covers, so the
difference between "verified" and "synced" is stated rather than implied.

### Model updates

I searched for releases in the 21–27 August window. Three items were
corroborated:

| Item | Date | Where it went |
|---|---|---|
| GLM-5.3-Flash (Z.AI) | reported 26 Aug 2026 | Ticker, flagged *pricing unverified* |
| GLM-5.2 Turbo (Z.AI) | reported 17 Aug 2026 | Ticker, flagged *pricing unverified* |
| Claude 3 Haiku shutdown on Vertex AI | 23 Aug 2026 | Ticker, *Retiring* section |

Both Z.AI entries stayed **out of the priced catalogue**. Third-party trackers
disagreed on pricing and there was no vendor page to check against — and the
existing policy in `CATALOG-UPDATE.md` is that guessing is worse than leaving a
gap and saying so.

Nothing shipped from Anthropic, OpenAI, Google or xAI in that window, so the
frontier entries are unchanged and still carry their 21 Aug verification stamps.

## 2. Modality summary dashboard

Selecting TTS, STT, Vision, Translation, Embedding, LLM or Code used to drop you
straight into an unsorted grid. Each modality now opens with a summary block
(`buildModalitySummary()`), rendered above the list on **both** the Explorer and
the Catalog page.

**KPI row** — models available, SaaS/API count, on-premises count, self-hostable
count, price range, provider count.

The price band is modality-aware, because a per-token range is meaningless for
speech:

- STT → `$/audio minute`
- TTS → `$/1M characters`
- everything else → `$/1M input tokens`

**Where it's hosted** — bar-ranked across Google (Vertex AI / AI Studio), Azure
AI Foundry, AWS Bedrock, Core42 Compass, OpenAI API, Alibaba DashScope, IBM
watsonx, and self-host / NVIDIA NIM.

**Deployment reality** — explicit YES/NONE on managed SaaS, on-premises,
self-host (open weights), and air-gap capability.

**Usable in <active country>** — the full sovereignty split, following whichever
country is selected on the Sovereignty page.

**Top providers** — the five with the most entries in that modality.

Two warnings fire from the data rather than being hard-coded:

- Every model in the modality is vendor-hosted SaaS → flags that there is no
  on-prem or air-gapped route at all.
- Nothing runs in-country as a managed service but open weights exist → flags
  that self-hosting is the only path to in-country inference.

The block closes with a scroll cue into the full model-by-model detail.

## 3. Sovereignty — rewritten per country

### The engine was UAE-shaped

`getModelStatusForCountry()` matched each model's `sovereignty.regions` array
against cloud-zone regexes. That array was written UAE-first, so every other
country fell through to "Not in Country" **and the cards still printed
`AWS me-central-1 (UAE)`** as the region tag.

Germany returned **0 sovereign models**.

The resolver now works in six ordered steps:

1. **Open weights** → self-host, sovereign wherever you deploy it.
2. **In-country evidence** — a region string naming a datacentre inside the
   selected country. Tokens are derived from each country's own `infra` list,
   skipping entries the data already marks "nearest" / "closest" / "nearby".
3. **In-bloc evidence** — a region inside the country's legal or regional bloc.
4. **Platform reach** — the serving platform runs regions in-country but this
   model's presence there is unconfirmed. The note says exactly that instead of
   pretending to know.
5. **On-prem fallback** — no in-country SaaS, but the vendor ships an on-prem build.
6. **Neither** — data leaves the country, with the actual serving zones named.

Region tags on the cards now come from this resolution, not from the model's
UAE-first array.

### A new "in-bloc" tier

Four blocs are defined (`SOV_BLOCS`), each marked `legal` or `regional`:

| Bloc | Strength | Basis |
|---|---|---|
| EU / EEA | **legal** | GDPR intra-EEA transfer + EU AI Act. UK and Switzerland included via adequacy |
| GCC | regional | Geographic proximity only — **no automatic cross-border adequacy** |
| Asia-Pacific | regional | Proximity only — each jurisdiction sets its own rules |
| North America | regional | Proximity only — US CLOUD Act exposure applies to US regions |

This is the distinction that actually matters in procurement: "lawful under
GDPR" and "physically resident in Germany" are different answers to different
questions, and collapsing them into one green badge would mislead.

**Germany, before → after:**

| | Before | After |
|---|---|---|
| Sovereign (in-country) | 0 | 2 |
| Compliant via EU/GDPR | — | 29 |
| Needs verification | 36 | 42 |
| Self-host | 18 | 18 |
| Not compliant | 91 | 54 |
| **Usable routes** | **18** | **91** |

Worth flagging: Saudi Arabia, Bahrain and Qatar now show 65–82 models as GCC
**regional** rather than compliant, because the Core42 Compass catalogue is
UAE-hosted. For a Saudi buyer that is a cross-border transfer with no automatic
adequacy, and the UI says so explicitly rather than counting it as sovereign.

### The UAE hard-coding leaked well beyond that page

A single `ACTIVE_COUNTRY` (default `UAE`) now drives everything. Selecting a
country on the Sovereignty page re-renders the Explorer and Catalog with it.

Previously hard-coded to the UAE, now country-aware:

- `sovBadgeFor()` — Explorer card badges
- `sovBannerFor()` — model detail modal, which now also shows the resolved
  regions and states which country it was evaluated against
- Explorer sovereignty filter chips (`🇩🇪 In-country only`, `✅ Germany or
  EU-compliant`)
- The Explorer's inline legend — was five hard-coded UAE sentences in the HTML,
  now rendered from the active country
- The Sovereignty page status legend, summary cards, and group headers
- `getFiltered()` sovereignty filtering, which read `m.sovereignty.uae` directly

## 4. Bugs fixed

### `selectCountry()` was crashing — this is the "it still shows UAE" symptom

The Pulse page reuses the `.sov-pill` class for **static `<span>` labels with no
`onclick`**. `selectCountry()` ran a document-wide query and called
`.getAttribute('onclick').includes(...)` on every match:

```js
document.querySelectorAll('.sov-pill').forEach(p =>
  p.classList.toggle('active', p.getAttribute('onclick').includes("'all'")));
//                             ^ null on the Pulse labels
```

It threw **before reaching `renderSovereignty()`** on the very next line. So
picking Germany left the previously rendered country's analysis on screen,
untouched. That is almost certainly what you were seeing.

`setSovFilter()` had the same pattern. Both now use a `sovPills()` helper scoped
to `#page-sovereignty` and matching `.sov-pill[onclick]`, with a null guard on
the attribute read. The `.sov-qs-btn` loop got the same guard.

### The Sovereignty Tip was pinned to the first country you ever selected

`renderRecommended()` inserted the tip with `insertAdjacentHTML('afterend', …)`
and then pruned duplicates:

```js
el.insertAdjacentHTML('afterend', `<div class="sov-tip">… ${cp.name} …</div>`);
const tips = document.querySelectorAll('#sovAnalysisPanel .sov-tip');
if (tips.length > 1) tips[0].remove();   // ← removes the NEW tip
```

`afterend` inserts the new node **before** the previous one in document order,
so `tips[0]` was the tip just created. Every render deleted the new tip and kept
the stale one. Select UAE, then Germany, then Japan — the tip still read
*"Sovereignty Tip for United Arab Emirates: Falcon 3 (built by TII Abu Dhabi)…"*.

The tip now writes into a fixed `#sovTipBox` container, so there is only ever one
and it always matches the selected country.

### Country chips accumulated instead of replacing

Selecting a country pushed it onto a rolling list of the last four, so previous
countries stayed on screen next to the current one. The selector now shows the
selected country only, with an ✕ to clear.

`clearSovCountry()` is new: it blanks the header, summary, grid, recommendations,
tip, legend and cloud table, un-highlights the quick-select buttons, and returns
the page to the default explainer state — so nothing from a previous country can
survive a reset.

### Every country had dead recommendations

The 21 Aug retirement pass removed `claude37`, `claude35` and `bloom` from the
catalogue but never updated `COUNTRY_PROFILES[*].recommended`. All 28 countries
referenced at least one dead ID, silently rendering fewer cards than intended
(Nigeria rendered 2 of 4).

Added `RETIRED_MODEL_REMAP` + `resolveModelId()`, mapping retired IDs to their
successors — `claude37` → `claude-sonnet-5`, `claude35` → `claude-haiku-45`,
`bloom` → `falcon3-40b`, and so on. A test asserts no country resolves to an
empty list.

### Load-order fragility

`activeCountryName()` / `activeCountryFlag()` are called from `initExplorer()`,
which can fire before the `COUNTRY_PROFILES` const further down the file has
initialised — a temporal-dead-zone `ReferenceError`. All country lookups now go
through a guarded `_cprof()` helper.
